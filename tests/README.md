# Pico tests

All test bodies, mocks, fixtures and checklists are outside production source. Rust production modules contain test-file declarations only, preserving access to private helpers without exporting them or copying their implementations.

## Commands

From the project root:

```sh
npm test
npm run test:backend
npm run test:frontend
npm run test:types
npm run test:ui-rendering
```

`npm test` runs backend, frontend, UI-rendering and test-source type checks, continuing through suites even if an earlier one fails. It exits nonzero for real test failures. It does not start the Android app, connect/pair with a real phone, change debugging settings or copy personal data. Backend fixtures use generated temporary files and an isolated fake ADB subprocess. Rust backend fixture cases require Unix/macOS and `python3`; the actual app targets macOS.

After a clean dependency install (`npm ci`), install the matching layout engine with `npx playwright install webkit` if required. The UI test server binds only to `127.0.0.1:1421`. A sandbox that blocks listening or spawning WebKit requires permission to run that suite outside the sandbox. Missing WebKit prints four explicit SKIPs; assertions failing after launch are FAILs.

## Separate responsibilities

- `src-tauri/tests/unit/`: original parser/filesystem helper cases.
- `src-tauri/tests/backend/`: subprocess, file/tree integrity, conflict/publication, cancellation, progress, preview and simulated device/wireless cases. Shared setup lives in `support.rs` and `fixtures/fake_adb.py`.
- `src-tauri/tests/parser_regression.rs`: existing standalone example migrated to an actual Cargo integration test.
- `tests/frontend/`: real components/hooks with a mocked Tauri bridge. Logic/accessibility assertions; no claims about OS layout or Android transport.
- `tests/ui-rendering/`: four WebKit cases for geometry, virtualisation, pointer targeting and reachable controls. Uses actual CSS/components/virtualiser, not a second full frontend functional suite.
- Manual actual-app/macOS and USB/Wi-Fi acceptance is done with a real phone before each release; it is excluded from the automated suite.

## Manual acceptance before pushing

Before a release, exercise the actual app with a real phone over USB and Wi-Fi: browsing, uploads/downloads, conflicts, cancellation, Finder drag, previews and pairing. Record PASS, FAIL, SKIP with a reason, or NOT RUN for each check/transport. No real phone is required for `npm test`; it does not emit device/native acceptance results. The old prerequisite-only reporters and their reporting tests have been removed.

## Reports and regression fixes

Generated reports live in ignored `tests/reports/`: frontend assertions, WebKit results/artifacts and aggregate automated suite exit codes. Rust results are printed by Cargo. Fresh output replaces earlier JSON; check the current command result/date before using a report. Manual results are recorded separately, not generated by the test runner.

The five original frontend regressions now pass after approved source fixes. They remain ordinary assertions, with additional related race/routing checks.

## Coverage limits

This baseline covers all currently wired feature areas with representative scenarios. It does not exhaust every input or race interleaving, Android version/manufacturer, filesystem or memory-leak possibility. Native protocol/transport/profile checks remain separate. Examples for expansion are full metadata timeout recovery, publication-time cancellation barriers, real disk-space limits, command hangs during upload staging/cleanup, wider Unicode/listing formats, and native delegate/descriptor profiling. These are not represented as implemented passing tests.
